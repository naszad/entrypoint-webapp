# GPA Utility Functions

This document outlines the purpose, inputs, and execution model for the helper routines that power GPA calculations throughout the EntryPoint SRM web application.

## Overview

All GPA lookups ultimately flow through a pair of Postgres routines:

- `public.calculate_gpa_for_students(...)` – batch-oriented entry point that accepts an array of `student_id` values and returns a two-column table (`student_id`, `gpa`).
- `public.calculate_gpa_dispatch(...)` – per-student dispatcher that selects the correct calculation strategy (simple, credit-hour weighted, added value, etc.) based on configuration values associated with the student’s school.

These routines live in the `public` schema and are invoked extensively by the `views.student_profiles` projection as well as by direct analytics queries.

### Data Sources

The GPA helpers depend on:

- `student_grades` – primary grade records
- `sections`, `courses`, and `terms` – contextual metadata used to scope grades by course or term
- `school_student_link` / `schools` – resolve school membership so we can derive the proper GPA method, credit mappings, and grade codes via configuration rows

Because all of those tables remain protected by row-level security (RLS), the helpers must be able to read *every* grade that should impact a student’s cumulative GPA, even when the caller’s JWT would normally hide portions of the gradebook.

## SECURITY DEFINER rationale

Both `calculate_gpa_for_students` and `calculate_gpa_dispatch` are declared `SECURITY DEFINER`. This is different from much of our database objects, in that they execute with the privileges of their owner (the migration assigns ownership to `postgres`) rather than inheriting the limitations of the calling user. We do this for two reasons:

1. **Consistency of GPA results.** GPA is a historical aggregate. If a counselor only has access to a subset of grade records due to RLS, running the calculation with caller rights would produce a lower score than the real value (grades outside their visibility would be ignored). Using `SECURITY DEFINER` guarantees the calculation always sees the student’s entire grade history, so the value matches the district’s source system.
2. **Shared caching/projections.** Views such as `views.student_profiles` are consumed by automated workflows (including AI-assisted SQL) that rely on stable, role-independent GPA values. With invoker rights, different roles would produce different GPA outputs, leading to inconsistent analytics and incorrect query answers.

### Guardrails in place

To keep these elevated privileges contained:

- We pin the function `search_path` to `public, pg_temp` (see migration `20251030200000_set_search_path_for_public_functions.sql`) so the functions resolve only the expected tables.
- The functions remain read-only—they never perform inserts/updates—so callers cannot bypass RLS to change data.
- RLS is still enforced everywhere else. The functions simply aggregate the full grade set and return the resulting GPA, which can then be shared safely.

## Function Signatures

```sql
-- Batch helper
calculate_gpa_for_students(
  p_student_ids    uuid[],
  p_method         text DEFAULT NULL,
  p_grade_codes    text[] DEFAULT NULL,
  p_credit_types   text[] DEFAULT NULL,
  p_year_labels    text[] DEFAULT NULL,
  p_grade_levels   integer[] DEFAULT NULL
) RETURNS TABLE(student_id uuid, gpa numeric)

-- Per-student dispatcher
calculate_gpa_dispatch(
  p_student_id     uuid,
  p_method         text,
  p_grade_codes    text[],
  p_credit_types   text[],
  p_year_labels    text[],
  p_grade_levels   integer[]
) RETURNS numeric
```

### Typical Call Flow

1. `calculate_gpa_for_students` receives a list of students (often generated by `views.student_profiles`).
2. The function inspects the first student’s school configuration to work out the GPA methodology (simple, credit-hour weighted, etc.). Callers can override this by passing `p_method` explicitly.
3. The helper delegates each student to `calculate_gpa_dispatch`, which in turn invokes the appropriate specialized routine (`calculate_simple_gpa`, `calculate_credit_hour_weighted_gpa`, `calculate_added_value_gpa`, etc.).
4. The final result is a set of rows that pair each student with their numeric GPA.

## When to call these functions

- Building projections or reporting views that need up-to-date GPAs.
- Ad-hoc analytics for GPA "sliced" by dimensions like grade codes or credit types.
- Any API or workflow that must respond with the canonical GPA value regardless of who requests it.
